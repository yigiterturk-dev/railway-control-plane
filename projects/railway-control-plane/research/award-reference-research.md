## ANLADIĞIM ARAŞTIRMA HEDEFİ

1. Project type: web application / developer tool / cloud-infrastructure control surface.
2. Area under study: lifecycle workflow-state visualization, activity ledger, navigation and operational hierarchy; secondarily public repository/README presentation.
3. Problem: make an opaque asynchronous cloud action legible, traceable, recoverable and trustworthy for engineers and interview reviewers.
4. Creative property: calm, precise, accountable operational UI; a visible state rail that resolves into a durable activity record.
5. Exclusions: Railway interface or brand imitation, generic SaaS metric-card grids, decorative terminals, purple/neon cloud aesthetics, hidden destructive actions, copied assets/code/layouts, unsupported scale claims.

## Ten provisional reference cards

These cards are proposed for Project Zero Gate 4 approval. “Use” means abstract principle only; it does not authorize visual copying or implementation.

### R01 — Arlanda Departure Sequencing Tool

- Source: https://awards.ixda.org/projects/arlanda-departure-sequencing-tool.html
- Status: candidate; provisional approval recommended.
- VERIFIED: IxDA archive identifies a 2016 professional Production project. The official case reports layering by importance, reducing clutter by two-thirds, immediate communication of actions, continuous real-world use and forecast-error reduction from 10 to 5 minutes.
- INFERRED principle: center the main composition on the ordered work queue; layer secondary evidence; preserve explicit manual overrides and communicate their downstream effect.
- Use for: horizontal lifecycle rail, current-stage emphasis, downstream consequences, calm density.
- Do not use for: aviation colors, runway imagery, exact line-up layout, or its claimed environmental figures without independent review.
- Unknown: accessibility conformance and current live availability.

### R02 — RCS 5 Boomer

- Source: https://awards.ixda.org/projects/rcs-5-boomer.html
- Status: candidate; provisional approval recommended.
- VERIFIED: 2014 IxDA professional Production project. Official case says the interface monitors/controls the rig and logs status, events and errors for later analysis; information is disclosed according to need and validated against industrial standards.
- INFERRED principle: a control surface earns trust when status, errors and later audit are one system rather than separate decorative widgets.
- Use for: state/event/error taxonomy, light/dark operational legibility, progressive disclosure.
- Do not use for: mining metaphors, icon set, exact industrial palette.
- Unknown: precise quantitative usability gains.

## Three anti-reference cards

### A01 — Generic metric-card dashboard pattern

- Evidence basis: canonical Project DNA and research context reject generic SaaS dashboard cards; several archive candidates center dashboards but do not show ordered action state.
- Reject: symmetrical three/four-card hero, undifferentiated KPIs, chart-first composition.
- Reason: it makes topology/metrics primary and hides the asynchronous lifecycle action that must be the product's signature.
- Exception: a small supporting metric may appear only when tied to a decision or workflow stage.

### A02 — Railway identity/interface imitation

- Evidence basis: explicit Project DNA, core brief and rejected-decision record.
- Reject: Railway layout, brand purple, logos, branded copy, dashboard structure, icons or screenshots as the visual source.
- Reason: harms originality, creates similarity risk, and weakens the project's value as independent product judgment.
- Exception: Railway name may appear factually when identifying the API/integration, subject to nominative-use review.

### A03 — Decorative terminal / optimistic-success theater

- Evidence basis: explicit Project DNA; operational references R01, R02 and R06 instead expose actual status, error, intervention and verified completion.
- Reject: fake command output, animated green checkmarks before server verification, hidden retries, silent destructive action.
- Reason: aestheticizes infrastructure while removing accountability.
- Exception: real, sanitized logs may be shown later as evidence, with accessible text and no secrets.

### VERIFIED

- IxDA's Arlanda case documents ordered operational sequencing, layered importance and downstream communication.
- IxDA's RCS case explicitly connects control, monitoring and status/event/error logging.
- UXDA's ESB rationale supports visualization matched to data type and a shared source of truth.

### OBSERVED

- Official archive text repeatedly frames successful operations tools around hierarchy, progressive disclosure, exceptions and human intervention.
- Webby pages for Resend, Tailscale and v0 expose award metadata but not enough UX rationale to support layout or conversion claims.

### INFERRED

- The strongest original combination for this project is not any one reference: Arlanda's sequence + RCS's event/error log + Acoustic Leak's verified completion + Flighty's ambient status.
- A ledger can serve both operator recovery and hiring-review evidence if each entry includes actor, requested action, stage changes, evidence and final disposition.
- Repository presentation should mirror the UI's trust model: claim → artifact/test/screenshot/live behavior, not marketing superlatives.

### UNKNOWN

- Accessibility, performance and responsive behavior for most archive projects.
- Conversion or hiring impact of any developer-tool website/README.
- Current live-project availability for most industrial and enterprise cases.
- Whether award-submission outcome claims were independently audited.
- Exact interaction timelines, motion curves, DOM/CSS and implementation choices; these were not inspected and are not authorized.

## Reusable principles

1. Order work around an explicit sequence; make the current stage glanceable.
2. Treat request, validation, dispatch, observation and settlement as distinct states with evidence.
3. Preserve status, events, errors and recovery attempts in one readable ledger.
4. Use progressive disclosure: primary action/state first, diagnostics second, implementation detail on demand.
5. Surface automation quietly; elevate exception, ownership and manual intervention.
6. Communicate the downstream effect of a user action immediately.
7. Match each visualization to a decision, not to a dashboard template.
8. Place volatile status where it remains continuously available.
9. Map public claims to evidence and name unknowns/limitations.
10. Use color as redundant signal, never the sole carrier of state.

Do not use these principles when they obscure actual API truth, encourage premature success, remove required confirmation, or reduce accessibility. The rail metaphor must remain original and functional, not a literal train illustration.
